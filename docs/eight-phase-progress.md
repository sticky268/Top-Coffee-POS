## Offline operating rules

- Successful API acknowledgement produces a server-confirmed order. Connection/time-out/5xx failures leave a durable local request, with the original UUID and exact payload.
- Pending orders are not included in confirmed sales reports and cannot print a paid receipt. The cashier must not collect a second payment merely because confirmation is delayed.
- Reconnection automatically retries pending requests while the signed-in app is open. Opening/resuming the application and selecting a branch restricts processing to that cashier and branch. Other users' requests remain stored until the original cashier signs in.
- The Pending Orders screen provides manual sync and explicit retry of rejected requests. Validation, price, permission, subscription and UUID conflicts remain for review; they are not silently overwritten or deleted.
- Offline catalog snapshots expire after 24 hours. Offline session restoration uses a device-protected snapshot no older than 8 hours, bound to the current token. New login and privileged management changes require the server. Server authorization is rechecked for every replay.
- Prices, stock, table availability and business permissions remain server-authoritative. A changed total blocks a new sale before stock/payment writes. An already accepted UUID returns the original sale without charging again, even if prices subsequently change.
- Offline data is isolated by API server, user and branch. The legacy Drift cache tables are retained for compatibility, but the outbox uses its own durable SQLite journal.
- If local persistence fails, checkout fails before sending a new request. Do not delete app data, uninstall, or reset the device while pending orders exist.
- Automatic retry is foreground app recovery, not a claim of background synchronization while the operating system has stopped the app. Reopening restores the saved queue.

## Evidence and release decision

The laptop acceptance batch uses code candidate `f04947266a72b374a7d9fd6338045cefe6170cb5`. The original checkout was updated successfully, preserving the generated-file snapshot in Git stash. Printer acceptance used an Android Pixel Tablet emulator connected to a physical network XP-N160II; offline acceptance used native Android persistence with a simulated transport and no real sales. The MySQL staging rehearsal retained the backup and isolated staging copy. Private credentials and database contents are not included in Git.

The initial integration harness omitted Flutter's `--no-uninstall` flag and reset emulator-local app data between runs. It was corrected, and the subsequent save/recovery run passed both phases and normal-app restoration. Backend sales were not altered by the fixture tests. Future native acceptance runs must preserve app data or use a separately identified test installation.

## Business review follow-up

The follow-up backend suite passed 311 tests / 1,355 assertions. Regression coverage now checks completed-payment report breakdowns, dashboard branch order numbers/split payments, archived-branch sales history, business isolation for administrators and branch-scoped models, nested product availability selectors, corrupt staff assignments, and inactive-account token reuse. Existing test fixtures explicitly associate staff with their branch's business.

A read-only audit of the retained laptop MySQL staging copy completed. Report/dashboard totals matched independent queries; stock ledgers and staff/order branch consistency checks passed. Four historical orders require payment reconciliation, and two legacy kitchen-only staff accounts require an owner policy decision. The audit did not rewrite sales, payments, stock, roles or working data. Detailed business records are retained locally rather than committed to the repository. These findings remain launch acceptance items.
